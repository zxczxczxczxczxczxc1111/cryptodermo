# Формат файла `vault.dat`

Это описание достаточно, чтобы написать независимый парсер и дешифратор
базы, не читая код приложения — только сам этот документ, стандартную
библиотеку любого языка (JSON, base64, PBKDF2-HMAC-SHA256, AES-256-GCM) и
пароль пользователя. Это прямое требование брифа (R24-R27, R57): если
однажды приложение не соберётся, данные всё равно должны быть читаемы.

Реализация в этом репозитории — `src/lib/vaultFormat.ts` (контейнер) и
`src/lib/crypto.ts` (криптография). Если этот документ и код когда-нибудь
разойдутся — код неправ, документ обновляется в том же тикете, где меняется
формат (правило зафиксировано в спецификации проекта).

## 1. Общий вид файла

`vault.dat` — это **один текстовый файл в кодировке UTF-8, содержащий ровно
один JSON-объект**. Никакого отдельного бинарного заголовка, никакого
конкатенированного бинарного тела после JSON — весь файл целиком открывается
любым текстовым редактором и парсится любым JSON-парсером. Секретны только
*значения* нескольких полей (они — шифротекст в base64), не структура файла.

Пример реального файла (перенос строк и отступы не имеют значения — это
просто JSON):

```json
{
  "v": 1,
  "kdf": {
    "alg": "PBKDF2-SHA256",
    "params": { "iterations": 5000000 },
    "salt": "q83jY1z2N0pC7fQxV8m3RA=="
  },
  "cipher": "AES-256-GCM",
  "iv": "3F2a91Bc0dE7aa==",
  "ct": "u2QpN7... (base64, длина зависит от размера базы)"
}
```

## 2. Поля заголовка

| Поле | Тип в JSON | Значение |
|---|---|---|
| `v` | число | Версия формата контейнера. Сейчас всегда `1`. Растёт при любом несовместимом изменении формата (не при изменении числа итераций конкретной базы — это не версия формата, а её параметр). |
| `kdf.alg` | строка | Алгоритм деривации ключа. Сейчас всегда `"PBKDF2-SHA256"`. |
| `kdf.params.iterations` | число (целое) | Число итераций PBKDF2, использованное **для этой конкретной базы**. Фиксируется один раз при создании базы (или при смене мастер-пароля) и с тех пор не меняется — разные файлы `vault.dat`, созданные в разное время или на разных машинах, могут иметь разные значения. См. §5. |
| `kdf.salt` | строка, base64 | Соль PBKDF2. Случайные байты, сгенерированные криптографически стойким генератором при создании базы. Формат не навязывает длину соли — парсер декодирует ровно то, что получилось из base64; на практике используется не меньше 16 байт (128 бит), как рекомендует NIST SP 800-132. |
| `cipher` | строка | Алгоритм шифрования тела. Сейчас всегда `"AES-256-GCM"`. |
| `iv` | строка, base64 | Вектор инициализации (nonce) AES-GCM. В этой реализации всегда ровно 12 байт (96 бит) — рекомендация NIST SP 800-38D для GCM — и генерируется заново на **каждое** сохранение, даже для той же базы. Не секрет, живёт открытым текстом в заголовке. |
| `ct` | строка, base64 | Зашифрованное тело базы. См. §4 — включает в себя тег аутентификации GCM, не только сам шифротекст. |

Base64 — стандартный алфавит (`A-Za-z0-9+/`) с паддингом `=`, как отдаёт
`btoa`/большинство стандартных библиотек по умолчанию (RFC 4648 §4, не
URL-safe вариант).

### Неизвестная версия `v`

Если `v` не равна поддерживаемому этой реализацией значению (сейчас — только
`1`), парсер обязан отказать явной понятной ошибкой и остановиться. Не
пытаться разобрать оставшиеся поля так, будто версия совпала, не подставлять
дефолты за отсутствующие поля новой версии — R07 (данные должны читаться
через десять лет) требует, чтобы чтение либо было правильным, либо явно
отказывало, но никогда не было тихо неправильным.

## 3. Деривация ключа (PBKDF2-SHA256)

Вход:
- **Пароль** — UTF-8-байты пароля пользователя ровно как он его ввёл.
  **Никакой нормализации Unicode (NFC/NFD/NFKC) и никакой обрезки пробелов
  не выполняется.** Это важно для совместимости: если пользователь на разных
  машинах вводит пароль с буквами, которые ОС может представить разными
  последовательностями кодовых точек (например, «й» как одна кодовая точка
  или как «и» + комбинирующий знак), UTF-8-байты будут разными — и получится
  разный ключ. Собственный парсер должен брать байты пароля как есть, без
  предварительной нормализации, если хочет получить тот же ключ.
- **Соль** — байты из `kdf.salt` после base64-декодирования.
- **Число итераций** — `kdf.params.iterations`.
- **Хеш-функция** — SHA-256 (это и есть смысл `-SHA256` в `kdf.alg`).

Выход: 256-битный (32-байтный) ключ, используемый напрямую как ключ
AES-256-GCM ниже (PBKDF2 с этими параметрами и есть весь путь от пароля до
ключа — отдельного шага KDF→HKDF или подобного нет).

Псевдокод (буквально то, что делает `crypto.subtle.deriveKey` с параметрами
из этой реализации):

```
key = PBKDF2(
  password = utf8_bytes(user_password),
  salt = base64_decode(header.kdf.salt),
  iterations = header.kdf.params.iterations,
  hash = SHA-256,
  output_length = 32 bytes  // 256 бит
)
```

## 4. Шифрование тела (AES-256-GCM)

- **Ключ** — 32 байта из §3.
- **IV/nonce** — `iv` из заголовка после base64-декодирования, 12 байт.
- **Additional Authenticated Data (AAD)** — не используется (пустая/отсутствует).
- **Тег аутентификации** — 128 бит (16 байт), длина по умолчанию для
  AES-GCM в WebCrypto (`AesGcmParams.tagLength` не задан явно этой
  реализацией => берётся дефолт спецификации, 128 бит). **Тег дописан в
  конец `ct`, а не хранится отдельным полем**: после base64-декодирования
  `ct` первые `N - 16` байт — это собственно шифротекст, последние 16 байт —
  тег. Это стандартное поведение WebCrypto (`crypto.subtle.encrypt` для
  AES-GCM отдаёт шифротекст с дописанным тегом; `crypto.subtle.decrypt`
  ожидает их на входе точно так же, одним куском) и совпадает с тем, как
  многие сторонние библиотеки ожидают комбинированные данные для GCM
  (например, `AESGCM.decrypt` в Python `cryptography.hazmat.primitives.ciphers.aead` —
  это стандартное поведение самой библиотеки, стоит свериться с её
  документацией на момент использования, а не полагаться только на этот
  абзац).

Расшифровка (обратная операция): AES-256-GCM с ключом из §3, `iv` из
заголовка и объединёнными шифротекст+тег из `ct` проверяет тег
аутентификации и либо отдаёт исходные байты тела, либо отказывает целиком —
частичной/повреждённой расшифровки не бывает. GCM не различает на своём
уровне «неверный ключ» и «повреждённые данные»: и то, и другое даёт один и
тот же отказ проверки тега. Собственный парсер, как и это приложение,
не должен пытаться различить эти два случая — их и невозможно достоверно
различить.

### Ловушка: AES-GCM часто НЕТ в стандартной библиотеке

Если вы пишете свой парсер/дешифратор на другом языке, не рассчитывайте,
что AES-256-GCM найдётся «из коробки» в стандартной библиотеке — во многих
языках это не так. Например, стандартная библиотека Python не содержит ни
одного примитива AES (ни блочного шифра, ни тем более режима GCM) —
ни в `hashlib`, ни в `ssl`, ни в `hmac`, нигде. PBKDF2-HMAC-SHA256 из §3
в Python есть «из коробки» (`hashlib.pbkdf2_hmac`), а вот AES-256-GCM из
§4 — нет.

Столкнувшись с этим в собственном `emergency-decrypt.py` этого проекта
(Python, только стандартная библиотека, без `pip install` — то же
требование, что и у стороннего разработчика с нуля), решение было такое:
второй текстовый файл, `aes_gcm.py`, лежащий рядом — самостоятельная
реализация AES по FIPS-197 и GCM по NIST SP 800-38D, написанная по
стандарту, а не изобретённая заново, и проверенная официальными тестовыми
векторами NIST/FIPS-197 (не только сверкой с этим же проектом — см.
комментарии и тесты в `aes_gcm_test.py`). Он — рабочий референс для
реализации AES-256-GCM с нуля на любом языке, где готового примитива нет:
структура (S-box и раундовые константы построены алгебраически, а не
скопированы табличными значениями; GF(2^128)-умножение, GHASH, GCTR,
J0 — по разделам NIST SP 800-38D §6-7 буквально) переносится на другой
язык почти построчно.

## 5. Число итераций PBKDF2: как оно выбрано

Нижняя граница — 600 000 итераций, рекомендация OWASP на момент написания
брифа. Но целевое время разблокировки важнее фиксированного числа:
приложение подбирает число итераций так, чтобы деривация ключа занимала
**0.5-1 секунду на машине пользователя** (компромисс между защитой от
подбора пароля и удобством ежедневной разблокировки).

Подбор — функция `benchmarkIterations(password, salt, targetMs)` в
`src/lib/crypto.ts`. Она делает ровно следующее: один разогревочный прогон
PBKDF2 на `CALIBRATION_ITERATIONS` (1 000 000) итераций, результат которого
не учитывается (первый вызов обычно медленнее следующих — прогрев
движка), затем `CALIBRATION_TRIALS` (7) учитываемых прогонов на том же
числе итераций, из времени которых берётся медиана. Медиана даёт время на
одну итерацию на этой машине, дальше линейная экстраполяция до `targetMs`
(PBKDF2 линеен по числу итераций — каждая итерация независимый раунд HMAC,
так что экстраполяция точна без многошагового подбора). Медиана нескольких
прогонов, а не один короткий замер, — потому что единичный короткий прогон
на практике оказался слишком шумным (см. цифры ниже). Результат никогда не
опускается ниже 600 000, даже если экстраполяция для очень быстрой машины
предложила бы меньше.

Итоговое число итераций **фиксируется в заголовке конкретной базы**
(`kdf.params.iterations`) в момент её создания (или при смене
мастер-пароля) — это не глобальная константа формата, разные базы могут
иметь разные значения в зависимости от того, на какой машине и когда они
были созданы.

`DEFAULT_ITERATIONS` в `src/lib/crypto.ts` — значение, которым приложение
пользуется при создании новой базы (пока пользователь не запросит
пересчитать под свою машину явно). Замер и выбор этого конкретного числа —
на машине разработки 16.08.2026, с целью 750мс (середина диапазона 0.5-1с):

- ранняя версия замера — один короткий прогон на 200 000 итераций без
  медианы — на этой машине давала оценку итогового числа итераций с
  разбросом почти в 2 раза между запусками (машина делит CPU с другими
  процессами), поэтому `benchmarkIterations` в итоге и делает медиану
  нескольких более длинных прогонов, а не один короткий — см. абзац выше;
- калибровка тем методом, который в итоге и реализован в
  `benchmarkIterations` (медиана 7 прогонов по 1 000 000 итераций),
  экстраполяция до 750мс дала **5 031 237** итераций;
- это число вручную (не автоматически, `benchmarkIterations` этот шаг не
  делает) округлено вниз до **5 000 000** — круглое число с небольшим
  запасом против случайной просадки производительности машины;
- округлённое число вручную перепроверено прямыми прогонами именно на
  5 000 000 итерациях: медиана 6 прогонов **804.7мс**, разброс
  739.6-828.5мс — весь разброс внутри целевого диапазона 0.5-1с.

Число не «из головы» — калибровка и экстраполяция воспроизводимы вызовом
`benchmarkIterations("...", salt, 750)` в `src/lib/crypto.ts` на любой
машине (точное число будет отличаться от запуска к запуску — это живой
замер времени, а не константа; округление до 5 000 000 и финальная
перепроверка выше — разовое ручное решение при выборе `DEFAULT_ITERATIONS`,
не то, что делает сама функция).

## 6. Тело после расшифровки

После успешной расшифровки (§4) получившиеся байты — это снова UTF-8 JSON
текст: массив записей приложения (`Item[]`). Точная схема записи — забота
`src/lib/vaultStore.ts`, не `vaultFormat.ts`/`crypto.ts` (эти два модуля не
знают и не проверяют, что лежит внутри расшифрованных байт, только
шифруют/расшифровывают и упаковывают их в контейнер). Схема на момент
написания этого документа (см. `spec.md` §3 «Модель записи» — источник
истины, если разойдётся с этим списком):

```ts
type Item = {
  id: string;
  type: 'login' | 'note' | 'card' | 'key' | 'other';
  title: string;
  tags: string[];
  fields: { name: string; value: string; secret: boolean; group?: string }[];
  note: string;
  attachments: { id: string; name: string; mimeType: string; size: number; data: string /* base64 */ }[];
  createdAt: string;
  updatedAt: string;
  history?: { fields: { name: string; value: string }[]; changedAt: string }[];
  pinned?: true;
};
```

Тело — просто `JSON.stringify(items)`, закодированный в UTF-8 байты перед
шифрованием (`Item[]`, не обёрнутый в дополнительный объект).

### 6.1 Поле `attachments` (вложения файлов, R44)

Каждый элемент `attachments` — одно вложение, целиком, внутри записи (не
ссылка и не отдельный файл на диске — см. §1: весь `vault.dat` остаётся
одним файлом, это осознанное решение §18 спецификации, ради атомарности и
портативности «бесплатно»):

| Поле | Тип | Значение |
|---|---|---|
| `id` | строка | Идентификатор вложения внутри записи (UUID, генерируется приложением при прикреплении файла). |
| `name` | строка | Имя файла, как оно было на диске пользователя в момент прикрепления (только имя файла — без пути к каталогу). |
| `mimeType` | строка | MIME-тип, угаданный по расширению файла на момент прикрепления (диалог выбора файла не отдаёт настоящий MIME — см. `Editor.tsx`, `guessMimeType`). Не гарантированно точен, это подсказка для интерфейса, не проверяемое поле формата. |
| `size` | число | Размер исходного файла в байтах (до base64-кодирования). |
| `data` | строка, base64 | Содержимое файла целиком, тем же алфавитом base64, что и остальной формат (§2) — просто исходные байты файла, без какой-либо дополнительной обёртки. |

**Мягкие лимиты (R44.3), не часть формата как такового.** Приложение
предупреждает в интерфейсе (не отказывает в сохранении — приоритет 1
«данные не теряются» выше приоритета 4 «удобство»), когда одно вложение
крупнее `MAX_ATTACHMENT_SIZE_BYTES` (~25 МБ) или когда примерный размер
тела базы после добавления файла (`VaultStore.estimateSizeBytes()`)
превышает `MAX_VAULT_SIZE_BYTES` (~300 МБ) — обе константы в
`src/lib/vaultStore.ts`. Сторонний парсер/дешифратор может читать и писать
`data` любого размера — ничего в самом формате файла не проверяет и не
ограничивает размер вложений, лимиты выше существуют только в интерфейсе
этого конкретного приложения как предупреждение об отзывчивости (вся база
перечитывается и переписывается целиком на каждое сохранение, §5 — чем
крупнее файл, тем медленнее).

**`group` у поля (добавлено 17.08.2026) объединяет поля в один аккаунт внутри
записи.** В одной записи часто живут несколько учёток одного сервиса: три почты
gmail, у каждой свои логин, пароль и код двухфакторки. Поля с одинаковым
значением `group` образуют такой блок, поля без `group` относятся ко всей
записи целиком.

Поле необязательное, значение - произвольная строка, которую человек видит как
заголовок блока. Отсутствие `group` - валидное состояние (так выглядят все
записи, созданные до этого изменения), миграция не нужна. Независимому парсеру
достаточно трактовать `group` как подпись: на расшифровку и на смысл остальных
полей она не влияет.

Порядок полей в массиве сохраняется как есть и остаётся значимым для показа;
приложение не переупорядочивает поля при группировке.

**`pinned` (добавлено 17.08.2026) означает «запись закреплена наверху
списка».** Поле необязательное и записывается ТОЛЬКО со значением `true`:
снятие закрепления удаляет поле целиком, а не пишет `false`. Поэтому база, в
которой избранным не пользовались, не отличается от базы прежней версии, а
старый файл открывается новой версией без миграции (отсутствие поля читается
как «не закреплена»). Независимому парсеру достаточно трактовать любое
отсутствующее или ложное значение как «не закреплена».

Закрепление НЕ меняет `updatedAt`: это не изменение содержимого записи.

**История (R45, см. `history` выше) на `attachments` не распространяется**
— замена или удаление вложения не оставляет запись в `history`, в отличие
от изменения поля с `secret: true`.

**`emergency-decrypt.py --unpack-attachments DIR`** (необязательный флаг —
`python emergency-decrypt.py <путь-к-vault.dat> --unpack-attachments DIR`)
дополнительно к обычному выводу JSON в stdout декодирует `data` каждого
вложения в отдельный файл внутри `DIR`. Имя файла — `<id записи>-<имя
вложения>` (во избежание коллизий одинаковых имён файлов в разных
записях). Оба сегмента — данные из расшифрованного тела базы, то есть не
доверенные слепо, даже если для того, чтобы вообще дойти до этого кода,
уже нужен верный мастер-пароль: скрипт берёт только последний сегмент по
обоим разделителям каталога (`/` и `\`) и заменяет `..`/`.`/пустую строку
на `unnamed` перед склейкой пути (`_sanitize_path_component` в
`emergency-decrypt.py`) — без этого специально сконструированный
`vault.dat` с именем вида `../../evil` мог бы записать файл за пределами
`DIR` (path traversal).

## 7. Резюме для реализации с нуля

1. Прочитать файл как UTF-8 текст, распарсить как JSON.
2. Проверить `v === 1`, иначе отказать.
3. `salt = base64_decode(v.kdf.salt)`, `iv = base64_decode(v.iv)`,
   `ct = base64_decode(v.ct)`.
4. `key = PBKDF2-HMAC-SHA256(password_utf8_bytes, salt, v.kdf.params.iterations, output=32 bytes)`.
5. `plaintext = AES-256-GCM-Decrypt(key, iv, ciphertext_and_tag=ct, aad=none)`.
   Если проверка тега не прошла — неверный пароль или повреждённый файл,
   различить нельзя.
6. `plaintext` — UTF-8 JSON, массив `Item` (§6).
