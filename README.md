# Vault

Личное офлайн-хранилище зашифрованных записей. Tauri v2 + React + TypeScript
+ Vite на фронте, минимальный Rust-слой (только файловые операции).

## Команды

| Команда | Что делает |
|---|---|
| `npm install` | Установить зависимости фронта |
| `npm run tauri dev` | Запустить приложение локально (окно + hot reload) |
| `npm run tauri build` | Собрать `.exe` под Windows x64 |
| `npm test` | Тесты фронта (Vitest) |
| `cargo test` (в `src-tauri/`) | Тесты Rust-части |

## Портативность

По умолчанию `vault.dat` и каталог `backups/` создаются рядом с исполняемым
файлом приложения - ничего не пишется в `%AppData%` или реестр. Это позволяет
носить приложение и базу на флешке.

## Аварийный дешифратор (`emergency-decrypt.py`)

Если это приложение однажды не запускается или не собирается, а база нужна
прямо сейчас - `emergency-decrypt.py` расшифровывает `vault.dat` (или любой
файл из `backups/`) в обычный JSON, зная только мастер-пароль. Python 3,
только стандартная библиотека - ничего не нужно устанавливать (`pip`
не требуется).

Обязательно нужен файл `aes_gcm.py`, лежащий с ним **в одном каталоге**:
это собственная реализация AES и AES-GCM, которую `emergency-decrypt.py`
использует для расшифровки (в стандартной библиотеке Python нет ни AES,
ни какого-либо другого шифра - подробности и почему это не "своя
криптография" в обход правил проекта - в комментарии в начале `aes_gcm.py`).
Оба файла копируются вместе автоматически при каждом сохранении базы - рядом
с `vault.dat` и в каждую резервную копию в `backups/`. Если вы вручную
скопировали куда-то только `emergency-decrypt.py` без `aes_gcm.py` - он
откажет с понятной ошибкой на шаге расшифровки, а не упадёт непонятно как.

```
python emergency-decrypt.py путь/к/vault.dat
```

Пароль спрашивается интерактивно (ничего не отображается при вводе). Флаг
`--unpack-attachments КАТАЛОГ` дополнительно распаковывает вложения файлов
из записей в отдельные файлы в указанном каталоге.

## Синхронизация базы через облако (Dropbox, Яндекс.Диск и подобные)

Приложение само ничего никуда не синхронизирует - никакой сетевой
синхронизации внутри него нет и не будет. Но `vault.dat` - один файл, а
`backups/` - обычный каталог рядом с ним, поэтому их можно вручную положить
в любую папку, которую синхронизирует облачный клиент (Dropbox, Яндекс.Диск,
OneDrive и т.п.). Это делаете вы сами, на свой риск - приложение не проверяет
и не настраивает это за вас.

Почему это в целом безопасно: каждое сохранение записывается атомарно
(`write_vault_atomic` - запись во временный файл рядом с целевым, `fsync`,
затем переименование поверх боевого файла). Значит, облачный клиент, который
сканирует каталог и подхватывает изменения, либо видит старую версию
`vault.dat` целиком, либо новую версию целиком - никогда "половину" файла в
процессе записи. Даже если синхронизация начнёт загружать файл в момент
сохранения, до переименования на диске всё ещё лежит старая, полностью
целая версия.

**Это не защищает от одного конкретного случая: правки на двух устройствах
одновременно.** Если вы откроете базу на ноутбуке и на компьютере в одно и
то же время, отредактируете что-то на обоих и оба сохранят изменения - облачный
клиент синхронизирует их как два независимых изменения одного файла. Обычно
это заканчивается либо тем, что более позднее сохранение молча перезаписывает
более раннее (правки с первого устройства теряются), либо тем, что облачный
клиент создаёт файл-конфликт (`vault (conflicted copy from ...).dat` и
подобные) - в обоих случаях это не то же самое, что потеря или порча данных
при записи (атомарность это по-прежнему гарантирует), но правки одного из
устройств можно не заметить. Если работаете с одной базой с нескольких
устройств - открывайте её на одном устройстве за раз, дожидайтесь окончания
синхронизации перед тем, как открыть на другом.
