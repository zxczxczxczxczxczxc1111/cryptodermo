## 1. Порядок фаз: структурная ошибка

Фаза 1 удаляла `--accent`, `--accent-soft`, `--font-mono`, оговаривая, что
использования переназначаются в фазах 2-7. Но `--accent` встречается **33 раза
в 11 CSS-файлах**, `--font-mono` в шести. Неопределённая custom property делает
объявление невалидным: `background: var(--accent)` станет прозрачным.

Итог: шесть коммитов подряд с заведомо сломанным интерфейсом, при том что каждая
фаза по регламенту заканчивается скриншотами. Скриншоты фаз 1-6 documented бы
поломку, а не прогресс, и `git bisect` по ветке стал бы бесполезен.

**Решение:** фаза 1 не удаляет, а переопределяет старые токены как алиасы на
новые (`--accent: var(--surface-selected)`, `--font-mono: var(--font-ui)`,
`--fs-mono: var(--fs-ui)`). Алиасы сносятся в фазе 9, когда
`grep -rn "accent\|font-mono" src --include=*.css` даёт ноль.

## 2. Риск №1 снят досрочно: в браузере не рендерится

Проверять нечего, ответ следует из кода:

- `App.tsx:299-317` при монтировании зовёт `determineInitialVaultPath()`;
- `App.tsx:115` -> `exeDir()` -> `tauriApi.ts:77` -> `invoke("exe_dir")`;
- `@tauri-apps/api/core.js:201-203` дёргает `window.__TAURI_INTERNALS__.invoke`.

В браузере это `undefined`, летит `TypeError`, `.catch` на `App.tsx:305` ставит
`bootstrapError`. Видно будет `App.tsx:635-641`: одну красную строку «Не удалось
определить расположение базы. Перезапустите приложение.» `LockScreen` не
смонтируется никогда.

**Заглушки одного `tauriApi` не хватит.** Официальные плагины импортируются
напрямую, мимо него (это разрешено архитектурой проекта):

- `@tauri-apps/api/window` -> `App.tsx:3`, `LockScreen.tsx:28` (вызов на `:1070`),
  `useAutoLock.ts:18`;
- `@tauri-apps/plugin-dialog` -> `App.tsx:2`, `Editor.tsx:2`, `RecordCard.tsx:2`,
  `ImportExportPanel.tsx:2`.

Заглушка обязана перехватывать три модуля через `resolve.alias` в
`vite.config.ts` под dev-флагом, **и отдавать не пустоту, а валидный
зашифрованный `vault.dat` плюс `vault.settings.json` с настроенным PIN** - иначе
`LockScreen` уйдёт в фазу `create` (`:1118`), и половина экранов, ради которых
всё затевается, останется невидимой.

Это не «dev-заглушка на фиктивных данных», а отдельная работа с правкой конфига
сборки.

## 3. Миграция `pinLength` расписана неполно

**Четыре точки записи настроек, которые про длину не знают:**

- `LockScreen.tsx:917` - настройка PIN при первом входе;
- `Settings.tsx:274` - настройка PIN из настроек;
- `Settings.tsx:289` - выключение PIN;
- `Settings.tsx:192` - инвалидация PIN при смене мастер-пароля.

Пропустить любую из двух последних - и останется `pinLength` без `pin`: экран
нарисует шесть ячеек там, где PIN уже выключен.

**Правило, без которого краснеют тесты:** `readSettings`
(`settingsConfig.ts:143-145`) читает поля поимённо, неизвестные ключи молча
выбрасываются. Поле надо делать по образцу `pin`/`pinLockout` - опциональным, без
дефолта. Тогда шесть `toEqual` на объект целиком
(`settingsConfig.test.ts:45,59,69,75,159,176`) проходят, потому что `toEqual`
игнорирует `undefined`. Если прописать `pinLength: 6` в `DEFAULT_SETTINGS` -
шесть тестов краснеют разом.

**`Settings.tsx:678,692`** - оба поля установки PIN имеют только
`maxLength={PIN_MAX_LENGTH}` и никакого выбора длины. Длина теперь не просто
валидируется, она фиксируется на будущее, значит экран настроек тоже правится.

**Дыра в самой миграции:** «просим ввести PIN обычным полем один раз» работает
только при успешном входе. У кого обёртка сломана (смена мастер-пароля
инвалидирует PIN, чистить её некому - записано в `CLAUDE.md`), длина не
запишется никогда, и человек навсегда останется на запасном поле. Это допустимо,
но должно быть написано.

## 4. Security-компромисс, который план протащил под ярлыком «только визуал»

`pinLock.ts:16-20` прямо описывает модель угроз: offline-подбор PIN по
украденному `vault.settings.json` смягчается числом итераций и лимитом попыток.

Сейчас атакующий не знает длину и обязан перебирать 4..8 цифр, это около
**111 млн** кандидатов. С записанным `pinLength: 6` остаётся **1 млн**, то есть
примерно в сто раз меньше. При 600k итераций PBKDF2 это всё ещё дорого, но
утверждение «схема настроек, ничего не затрагивается» неполное.

Размен может быть принят сознательно, но он должен быть **принят**, а не проехать
незамеченным.

## 5. Удаление JetBrains Mono: точечные риски

| Файл:строка | Что рисует |
|---|---|
| `StatusBar.css:47` | отсчёт автоблокировки |
| `RecordCard.css:232-234` | значения **секретных** полей + вложения (`:489`) |
| `Editor.css:144` | **все** значения полей редактора (`Editor.tsx:932`, без условия на `secret`) |
| `Settings.css:95` | **все** инпуты настроек, включая путь к базе |
| `LockScreen.css:88` | все поля входа |
| `PasswordGenerator.css:40` | превью сгенерированного пароля |

**Главная находка: `StatusBar.css:48` уже содержит
`font-variant-numeric: tabular-nums`** рядом с `font-family`. Отсчёт тикает раз в
секунду (`useAutoLock.ts:145`), формат `M:SS`. Inter поддерживает `tnum`, значит
достаточно убрать только `font-family` и **сохранить строку с `tabular-nums`**.
При механическом сносе всего блока она уедет вместе с ним - ровно та однострочная
регрессия, которую потом ловят неделю. Тот же `tabular-nums` нужно добавить на
счётчик «Записей» и на ячейки PIN.

**Расхождение по существу:** решение «наборы Inter только на паролях» не сходится
с фактами. Мона стоит на всех значениях редактора, всех инпутах настроек и всех
полях входа. Переход на пропорциональный Inter там - это отказ от различимости
`0/O` и `1/l/I` на путях, ключах и логинах. Требует отдельного решения.

**Не сломается:** выравнивания по моноширине в проекте нет, ни одной таблицы, ни
одного `ch`-юнита. Риск точечный, весь в таблице выше.

Плюс три места с `letter-spacing` под мону: `RecordCard.css:234` (`0.02em`),
`LockScreen.css:102` (`6px`, умирает вместе с ячейками) и тринадцать
`var(--ls-label)`, откалиброванных под Segoe UI - с Inter их скорее всего надо
уменьшать.

## 8. Лишнее и переусложнённое

1. **`vercel-react-view-transitions` - тупик.** Установлен React **19.2.8 stable**,
   `'ViewTransition' in require('react')` даёт `false`. Компонент живёт только в
   experimental-канале, то есть смена зависимости, что по правилам проекта (R31)
   требует отдельного вопроса. Рабочий путь для WebView2 - чистый CSS
   `view-transition-name` плюс `document.startViewTransition()`, React ни при чём.
2. **Полная матрица состояний в фазе 2** - спецификация для продукта с командой.
   Состояние «загрузка» на кнопках существует ровно в двух местах (`busy` в
   `LockScreen` и `Editor`). Рисовать его для «тихой» и «опасной» - работа в стол.
3. **Вес 300 при базовых 14px на тёмном фоне** - прямая угроза контрастности,
   ради которой в плане отдельный пункт и отдельный риск. Срезать до 400/500/600
   (шесть файлов), 300 добавить только если по факту не хватит ступени.
4. **Скриншоты после каждой фазы** - в фазах 1 и 2 менять видимого нечего.
   Регламент, выполняемый формально, перестаёт выполняться вообще.

## 10. Версия приложения в статус-баре

Замена «Версия формата: v1» не является чистой правкой строки. Два пути:

- `getVersion()` из `@tauri-apps/api/app` (разрешение есть, `core:app:default`
  включает `allow-version`) - но это ещё один IPC-вызов, который упадёт в браузере
  и сделает `StatusBar` асинхронным;
- `define` в `vite.config.ts` из `package.json` - проще и честнее.

Выбрать надо в плане, а не по ходу.
