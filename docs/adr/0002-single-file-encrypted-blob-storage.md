# 0002. Один зашифрованный файл-блоб вместо SQLite/SQLCipher

## Контекст

Нужно было выбрать модель хранения для персональных зашифрованных записей на десктопе
без сервера, читаемую независимым скриптом ещё через десять лет.

## Решение

Вся база — один файл `vault.dat`: открытый JSON-заголовок + одно зашифрованное тело с
массивом `Item[]`. Читается в память целиком при разблокировке, пишется целиком при
каждом сохранении. Ни SQLite, ни SQLCipher не используются.

## Почему

SQLite/SQLCipher рассмотрены и отклонены явно (R14): они добавляют бинарный формат со
своей внутренней структурой страниц, что усложняет ровно то, ради чего существует
аварийный Python-скрипт — возможность прочитать данные из первых принципов через десять
лет, зная только пароль (приоритет 2, см. ADR-0001). Единый файл-блоб также даёт
атомарность (перезапись целиком через tmp+fsync+rename) и портативность (одна папка на
флешке, R29) без отдельного протокола синхронизации файла БД с журналом транзакций.

## Последствия

Каждое сохранение перечитывает и переписывает всю базу целиком — при большом числе
вложений (§18 спецификации) это бьёт по отзывчивости, что и вызвало отдельное
предупреждение о размере (R44.3, ~300 МБ на базу). Нет частичных транзакций и нет
индексов на диске — поиск (R96) и виртуализация списка (R96.1) реализуются полностью в
памяти после расшифровки. Переход на SQLite/SQLCipher в будущем означает переписать
`vault-format`, `vault-store`, `vault_fs` и `emergency-decrypt.py` одновременно, а не
внести точечную правку.
