# 0004. Криптосхема: WebCrypto/PBKDF2-SHA256/AES-256-GCM, только пароль

## Контекст

Нужна деривация ключа и шифрование данных для MVP на десктопе, с пониманием, что
алгоритм и место реализации (JS vs Rust) могут смениться позже.

## Решение

Криптомодуль - WebCrypto (`crypto.subtle`) на JS, без Rust. KDF - PBKDF2-SHA256, ≥600000
итераций (нижняя граница OWASP из брифа, фактическое число - по бенчмарку на машине
пользователя). Шифр - AES-256-GCM со случайным IV на каждое сохранение. Ключ наружу
выдаётся только как непереносимый `CryptoKey` (`extractable: false`). Второго фактора
(ключ-файла) нет - только пароль.

## Почему

Рассмотрен вариант (б) из брифа - нативная реализация на стороне Rust вместо WebCrypto в
JS. Отклонён для MVP: WebCrypto - часть рантайма Tauri без дополнительных зависимостей, а
изоляция модуля за сигнатурой `derive/encrypt/decrypt` уже делает переход на Rust-крипту
в будущем заменой реализации, а не переписыванием приложения. Argon2id как альтернатива
PBKDF2 отклонён по той же логике: не входит в WebCrypto нативно, потребовал бы стороннюю
библиотеку сейчас ради выигрыша, не являющегося приоритетом 1-2 (ADR-0001). Ключ-файл как
второй фактор отклонён явно (R42, «нет, только пароль») - второй фактор означает второй
секрет, который тоже можно потерять, что прямо конфликтует с приоритетом 1.

## Последствия

Собственных алгоритмов в основном приложении нет нигде (R20/R32) - единственное
исключение появилось позже как discovery в аварийном скрипте (см. ADR-0009). AES-GCM не
различает «неверный пароль» и «повреждённые данные» на уровне тега аутентификации,
поэтому текст ошибки в UI один на оба случая - точность диагностики принесена в жертву
однородности сообщения. Число итераций PBKDF2 не пересчитывается на каждой разблокировке,
только один раз при подборе параметров - если машина пользователя сильно изменится
(апгрейд/даунгрейд), число итераций само не подстроится.
