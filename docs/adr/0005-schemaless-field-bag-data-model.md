# 0005. Записи без типизированной схемы - общий набор + массив fields

## Контекст

Записи пяти разных типов (login/note/card/key/other) должны редактироваться и
отображаться, при этом бриф заранее требовал: «один экран редактора обслуживает все
типы записей».

## Решение

Модель `Item` держит фиксированный, общий для всех типов набор полей (id, type, title,
tags, note, createdAt, updatedAt, history?) плюс один динамический массив
`fields: {name, value, secret}[]`, куда уходит всё специфичное для типа. Тип записи
используется только для предзаполнения набора полей у новых записей
(`defaultFieldsFor(type)`), не для валидации структуры.

## Почему

Альтернатива - типизированная схема на каждый `type` (например, отдельные обязательные
поля у `card` вроде номера и срока действия, отдельные у `key`). Отклонена: противоречит
R98/R19 (один экран редактора на все типы) и R18 дословно из брифа («фиксированных полей
мало, всё специфичное живёт в fields») - типизированная схема потребовала бы либо N
редакторов, либо один редактор с ветвлением по типу внутри, то есть ровно то усложнение,
которого бриф просил избежать.

## Последствия

Нет валидации на уровне формата данных, что поле `login`-записи действительно содержит
логин, а не что-то ещё - вся смысловая нагрузка на пользователе и на
`defaultFieldsFor`, который влияет только на создание новой записи, не на существующие.
Смена типа записи задним числом не пересобирает набор полей автоматически (щель между
тасками T07/T08, закрытая отдельным дозапросом - см. манифест R43). История (R45)
навешена только на элементы `fields` с `secret:true` - сформулировать это было бы сложнее
при типизированной схеме с именованными колонками.
