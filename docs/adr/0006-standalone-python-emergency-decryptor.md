# 0006. Аварийный дешифратор - самостоятельная копия логики на чистом Python

## Контекст

Приоритет 2 брифа - данные читаются через десять лет, даже если приложение однажды не
соберётся.

## Решение

`emergency-decrypt.py` - самостоятельная копия логики крипто- и формат-модулей на чистом
Python 3, без сторонних пакетов (только `json`, `base64`, `hashlib`, `getpass`), без
импортов из `src/` или `src-tauri/`, не собирается, лежит текстовым файлом рядом с
`vault.dat` и копируется в каждую резервную копию. Совместимость с текущим форматом
проверяется автотестом (R26): приложение создаёт базу → скрипт её открывает → JSON
совпадает; тест ломается, если формат изменился без обновления скрипта.

## Почему

Альтернатива - не дублировать логику, а дать скрипту зависеть от pip-пакета вроде
`cryptography` (короче и надёжнее в реализации). Отклонена: приоритет 2 требует
читаемости «даже если приложение не соберётся» - pip-пакет через десять лет может не
установиться на тогдашнем Python без интернета, а без сети `pip install` вообще не
выполнится. Другая альтернатива - не писать отдельный скрипт вообще, полагаясь только на
`FORMAT.md` как документацию для написания парсера с нуля в момент аварии. Отклонена:
работающий скрипт - проверенный код, документ - код, который ещё никто не запускал.

## Последствия

Логика крипто- и формат-модулей существует в двух независимых реализациях (TS/Rust и
Python), которые обязаны совпадать по результату - единственная защита от расхождения
между ними это автотест R26, а не архитектура языка. Любое изменение формата или
алгоритма шифрования - правка минимум в двух местах в одном тикете, не в одном. Скорость
`emergency-decrypt.py` не оптимизирована (R25) - осознанный компромисс, годный для
личного архива, но не для потокового использования.
