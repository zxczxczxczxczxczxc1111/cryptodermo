# 0011 (D03). Discovery: понадобилась пятая Rust-команда для портируемого пути

## Контекст (что предполагал план)

Правило файлового слоя фиксировало «ровно четыре» Rust-команды (R93, §6): `read_vault`,
`write_vault_atomic`, `list_backups`, `rotate_backups`. `App.tsx` (таск 12) должен
передать `LockScreen` обязательный проп `vaultPath: string`, а на самом первом запуске
`vault.settings.json` ещё не существует (см. ADR-0008), и `lastVaultPath` неоткуда взять.

## Решение (что доказал код)

Путь к базе обязан лежать рядом с исполняемым файлом, а не в `%AppData%` (R29) -
единственный переносимый способ узнать каталог исполняемого файла на Windows потребовал
проверки через Context7: `executableDir()` из `@tauri-apps/api/path` (Tauri v2) прямо не
поддерживается на Windows, только `std::env::current_exe()` на стороне Rust даёт нужный
результат. Добавлена пятая Rust-команда `exe_dir()` в `vault_fs.rs`, минимальная, по тому
же паттерну, что и остальные четыре; правило «ровно 4 команды» в `interfaces.md`
обновлено на «5».

## Почему

Альтернатива - получить каталог исполняемого файла средствами JS/Tauri API без похода в
Rust. Отклонена не по вкусу, а по факту: `executableDir()` (единственный подходящий по
названию API) документированно не работает на Windows, а Windows - единственная целевая
платформа этого проекта (R36). Другой альтернативы, кроме отдельной Rust-команды, для
этой конкретной ОС не существовало.

## Последствия

«Ровно 4 файловые команды» (R93, минимальная Rust-часть по R11) перестало быть буквально
верным ещё до того, как приложение было закончено; будущие ссылки на R93 или на границы
модуля `vault_fs` должны сверяться с `interfaces.md`, а не с исходным текстом
спецификации, где всё ещё написано «четыре». Любой будущий портируемый путь (не только
`vaultPath`) на Windows в этом проекте, скорее всего, тоже потребует Rust-команды, а не
решения на чистом JS - прецедент установлен.
